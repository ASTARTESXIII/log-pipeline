## 1. Данные
Для замеров был взят синтетический лог individual_log_olkov.csv, содержащий 100 000 строк (объём файла 4.01 МБ). Лог содержит поля timestamp, event_type, user, severity. Данные были сгенерированы скриптом с фиксированным сидом (np.random.seed(13)), чтобы результаты замеров можно было воспроизвести.

## 2. Задача
Количество событий по `event_type` за каждый час.

## 3. Реализация

**Pandas:**
```python
d = df.copy()
d["hour"] = d["timestamp"].dt.floor("h")
return d.groupby(["hour", "event_type"]).size().reset_index(name="count")
```

**DuckDB:**
```sql
SELECT date_trunc('hour', timestamp) AS hour, 
       event_type, 
       COUNT(*) AS count
FROM read_csv_auto('individual_log_olkov.csv')
GROUP BY hour, event_type
```

## 4. Замеры (медиана из 3 прогонов)

| Инструмент | Время (с) | Пиковая память (МБ)* | Удобство (1–5) |
|------------|-----------|----------------------|----------------|
| Pandas     | 0.0744    | 9.76                 | 5              |
| DuckDB     | 0.4361    | 0.02                 | 4              |

\* По `tracemalloc`. Реальное потребление памяти DuckDB выше, так как он написан на C++ и выделяет память вне контроля Python.

## 5. Вывод

На файле в 100 000 строк (4.01 МБ) Pandas оказался почти в 6 раз быстрее DuckDB по времени (0.0744 с против 0.4361 с). Это связано с тем, что данные уже были загружены в память Pandas (DataFrame `df`), а DuckDB в функции `agg_duckdb()` каждый раз заново читал файл с диска через `read_csv_auto`.

По памяти `tracemalloc` показал 0.02 МБ для DuckDB против 9.76 МБ для Pandas. Однако `tracemalloc` не видит C++-память DuckDB, поэтому эти цифры не совсем корректны для прямого сравнения.

Для этой задачи (простая агрегация) я бы выбрал Pandas, так как данные уже загружены в память и агрегация происходит мгновенно. Если бы данных было больше оперативной памяти (например, 10 ГБ), я бы выбрал DuckDB: он не требует загрузки всего файла в память и использует `read_csv_auto` для потокового чтения.
